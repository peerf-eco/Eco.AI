# V7 Architecture — three-agent orchestrator

> Canonical documentation is now maintained in the repository root
> `WORKING_DOCUMENTATION.md`. This file is retained as a compatibility note.

> Current production architecture as of 2026-05-25. The frontend label
> "V6 Five-Node Pipeline" is a hardcoded heading that hasn't been
> updated; the actual code path is V7 (see endpoint mapping below).

## Topology

```
User request
   ↓
architect  ──to_coder───→  coder  ──to_tester───→  tester  ──done──→ END
   │                        │                        │
   │                        │                        └──to_coder──→ coder
   │                        │                                       (retry)
   │                        └──to_architect──→ architect
   │                                            (plan escalation)
   │
   └──fail──→ END        ↓ all agents can fail honestly
```

Implemented by `agent/v6/orchestrator.py:Orchestrator` — a flat,
declared-edges design (the Microsoft Agent Framework / OpenAI Agents
SDK pattern, NOT a recursion-based stack). Wired up in
`agent/v6/entry.py:build_v7_pipeline`. Max-hop ceiling: 8 (guards
against mutual-handoff loops).

## Agents

Each agent is an `EcoAgent` instance with a fixed system prompt, a
fixed tool set, and one or more stop-tool names. The stop-tool name
the agent calls becomes the edge label the orchestrator follows.

| Agent | Module | Stop tools | Role |
|---|---|---|---|
| architect | `agent/v6/agents/architect.py` | `to_coder`, `fail` | Discover components, pull DEVKITs, design the application, hand off plan |
| coder | `agent/v6/agents/coder.py` | `to_tester`, `to_architect`, `fail` | Author C sources, build, fix build errors |
| tester | `agent/v6/agents/tester.py` | `done`, `to_coder`, `fail` | Run built artifact against acceptance criteria; iterate with coder on bugs |

Tools per agent: see `agent/v6/tools/README.md`.

## LLM integration

V7 talks to the LLM via `agent/pi_ai/` — an async OpenAI-compatible
streaming client that preserves `delta.reasoning` (the langchain_openai
1.2.1 wrapper drops it). This is what makes "thinking blocks" render
real reasoning text in the UI.

Per-call traces persisted to `traces/v7-<thread_id>/NN_*.json` — every
LLM request+response logged incrementally so debugging works even if
the agent loop never terminates.

## WebSocket endpoint

`/ws/v7/chat` in `backend/server.py` (around line 1020). Lifecycle:

1. Client connects, server resolves `project_dir`, `marketplace_cache_root`,
   `cli_path`, `make_exe`. Sends `heartbeat`.
2. Client sends `user_request`. Server builds a seed message:
   `_workspace_header(project_dir, marketplace_cache_root) + user_req`.
3. Phase 1 — architect runs. On `to_coder` → present plan to client
   (`plan_review_required`). HITL: client approves / rejects with feedback.
4. Phase 2 — sub-orchestrator runs coder ⇄ tester until `done` or `fail`.
5. Server emits `pipeline_done`.

UI label translation: the orchestrator runs `architect`, but the
WebSocket protocol uses V6 node names. The mapping at `server.py:1063`:

```python
NODE_OF  = {"architect": "planner",  "coder": "coder",   "tester": "tester"}
PHASE_OF = {"architect": "planning", "coder": "coding",  "tester": "testing"}
```

That's why the UI shows "Planning · PLANNER" even though the running
agent is architect.

## Workspace orientation

Every agent's seed message starts with a `=== Workspace ===` block
generated by `backend/server.py:_workspace_header`. It tells the model:

- Absolute `project_dir` (read-write)
- Absolute `marketplace_cache` root (read-only, all 30 components)
- How to explore via `grep` / `glob` / `read` (3 worked examples)
- Path anchoring rule (basename-prefix → root)
- Anti-duplicate-call reminder

This block is critical: without it, agents previously burned 30+
iterations on `list_dir('.')` / `list_dir('/')` path-guessing.

## V6 vs V7 — which is which

The codebase has both architectures side by side:

| | V6 (legacy) | V7 (current) |
|---|---|---|
| Style | Rigid LangGraph StateGraph | Flat agent orchestrator |
| Code | `agent/v6/nodes/*.py`, `agent/v6/graph.py` | `agent/v6/agents/*.py`, `agent/v6/orchestrator.py` |
| Endpoint | `/ws/v6/chat` | `/ws/v7/chat` |
| HITL | `plan_gate` + `escalate` interrupts | Plan-review loop in server |
| Toolset | `nodes/planner.py:make_planner_tools()` | `agents/architect.py:make_architect()` |
| Frontend | `NEXT_PUBLIC_PIPELINE_VERSION=v6` (rollback only) | `NEXT_PUBLIC_PIPELINE_VERSION=v7` (default, production) |

The `agent/v6/` directory name is misleading — it houses both. Kept as
`v6` to avoid renaming work mid-flight. Future cleanup may split into
`agents/legacy_v6/` and `agents/v7/`.

## RAG infrastructure

Lives in `agent/rag/` and `marketplace_index.sqlite`:

- **Index**: sqlite-vec + FTS5, 1217 chunks across 30 components,
  embedded with qwen3-embedding-8b (4096-dim).
- **Chunker**: AST-based via tree-sitter-c + cAST split-then-merge.
  Won evaluation against naive / recursive / structural strategies
  (Recall@5 = 1.00 on golden queries).
- **Retrieval**: vector_only (hybrid + RRF degrades Recall@5 on our
  corpus — the lexical branch finds different chunks and RRF downvotes
  the correct vector-#1).
- **Rebuild**: `python scripts/build_marketplace_index.py`.

See:
- `memory/project_rag_chunker_choice.md` for chunker eval results
- `memory/project_rag_retrieval_choice.md` for retrieval ablations
- `agent/v6/tools/rag.py` for the `search_marketplace` tool

## Build chain

Local toolchain (no network at build time):

- Windows: `cl.exe` via Makefile from MSVC_v140 templates, vcvarsall.bat
- Linux: `gcc` + `ar` argv (no shell=True, see PR #10)
- GNU Make via `V6_MAKE_EXE` (Windows: `C:\Users\gaevy\gcc\bin\make.exe`)

Critical build gotchas — see `memory/MEMORY.md` "Build gotchas" section
(path depth, MSYS_NO_PATHCONV, RegisterComponent cast, lowercase
methods, size_t redefinition, etc.).
