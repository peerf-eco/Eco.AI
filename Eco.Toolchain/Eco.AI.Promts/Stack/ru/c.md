# ТЕХНИЧЕСКИЙ СТЕК: ЯЗЫК C (ECO STANDARDS)

Этот документ определяет правила написания и форматирования кода для всех последующих файлов (`.c`, `.h`), которые будут собираться в рамках рецепта.

## 1. СТАНДАРТЫ ОФОРМЛЕНИЯ И КОМПИЛЯЦИИ ФАЙЛОВ
- **Стандарт языка**: Весь C-код должен строго соответствовать спецификации **C89 (ANSI C) - ANSI X3.159-1989**. Запрещены стандарты C99/C11 (например, объявления переменных внутри кода, комментарии `//`, `stdbool.h`). Все переменные объявляются строго в начале блока.
- **Стандарты безопасности**: Код должен соответствовать правилам **MISRA C** для обеспечения высокой надежности. В зависимости от требований ТЗ, ориентируйся на: 
  - MISRA C:1998 (1-я редакция, 127 правил).
- **Кодировка**: Все заголовочные файлы и файлы реализации должны быть строго в кодировке **UTF-8 с сигнатурой (BOM) / Codepage 65001**.
- **Выравнивание структур (`#pragma pack`)**: Использование директивы `#pragma pack` разрешено **исключительно** для структур данных, которые сериализуются (сохраняются) в файлы, передаются по сети или жестко привязаны к бинарным стандартам (где критично побайтовое выравнивание). Для обычных внутренних структур и объектов имплементации компонентов использовать `#pragma pack` **запрещено**, чтобы не нарушать естественное выравнивание процессора и не снижать производительность.
- **Шапки файлов (File Header)**: Каждый создаваемый файл обязан начинаться со следующего блока комментариев:
  ```cpp
  /*
   * <character encoding> Cyrillic (UTF-8 with signature) - Codepage 65001 </character encoding>
   * <summary> [Краткое описание назначения этого файла] </summary>
   * <description> [Детальное описание бизнес-логики или структуры] </description>
   * <reference> </reference>
   * <author> Copyright (c) 2026 [AUTHOR]. All rights reserved. </author>
   */
  ```

## 2. СТАНДАРТЫ ОФОРМЛЕНИЯ ФУНКЦИЙ И МЕТОДОВ
- **Документирование методов**: Каждая функция и каждый метод виртуальной таблицы (VTbl) снабжаются заголовком:
  ```cpp
  /*
   * <summary> [Что делает функция] </summary>
   * <description> [Подробности алгоритма, описание параметров и возвращаемых кодов] </description>
   */
  ```
- **Валидация указателей**: Любой метод интерфейса должен начинаться с жесткой проверки входящих данных на `NULL`:
  ```cpp
  if (me == NULL || ppv == NULL) {
      return ERR_ECO_POINTER;
  }
  ```

## 3. ДИСЦИПЛИНА ПАМЯТИ И ТИПОВ ДАННЫХ
- **Никаких стандартных типов C**: Запрещено использовать `int`, `char`, `long`, `void*`. Используйте исключительно типы Eco: `int16_t`, `char_t`, `byte_t`, `voidptr_t`. Все эти типы должны подключаться из обязательного базового компонента `Eco.Core1/SharedFiles` (см. правила поиска в ACOM).
- **Управление памятью**: Использование `malloc`, `calloc`, `free` категорически запрещено. Выделение памяти происходит только через аллокатор компонента `IEcoMemoryAllocator1` (из подсистемы `Eco.MemoryManager1`), доступный через поле `m_pIMem`:
  ```cpp
  pCMe->m_pIMem->pVTbl->Alloc(pCMe->m_pIMem, size);
  ```

## 4. ПРАВИЛА РАБОТЫ С ШАБЛОНАМИ И МАКРОСАМИ
- **Где искать шаблоны**: Если в техническом задании не указаны конкретные шаблоны кода, ИИ (в роли кодера) обязан брать базовые файлы-бланки из папки **`Templates/`** в корне репозитория (или текущей директории). 
  - Для **C** (`*.c`, `*.h`): использовать файлы `IdROOT.h`, `CROOT.h`, `CROOT.c` и т.д. из папки `Templates/`.
- **Замена макросов**: При работе с файлом-шаблоном ИИ должен полностью сохранить его структуру и заменить все текстовые маркеры в квадратных скобках (например, `[PROJECT_NAME]`, `[GUID_CID_FORMATED]`, `[AUTHOR]`) на реальные данные создаваемого проекта по правилам **ACOM**.
- **ОБЯЗАТЕЛЬНЫЙ ПОШАГОВЫЙ АЛГОРИТМ ГЕНЕРАЦИИ (СТРУКТУРА И ШАПКИ)**:
  ИИ **категорически запрещено** складывать все файлы в одну корневую папку и генерировать код без документации. Сборка проекта выполняется строго по шагам:
  1. **Шаг 1: Вывод дерева папок**: Первым делом выведи текстовую структуру каталогов будущего проекта согласно спецификации **ACOM** (включая `AssemblyFiles`, `HeaderFiles`, `SharedFiles`, `SourceFiles` и платформенные подпапки).
  2. **Шаг 2: Путь к файлу**: Перед генерацией каждого отдельного файла обязательно напиши его полный относительный путь жирным шрифтом. *Пример:* `Файл: SourceFiles/CEcoMath.c`.
  3. **Шаг 3: Обязательная шапка (File Header)**: Каждый маркдаун-блок кода обязан начинаться со стандартного комментария `File Header` из Раздела 1 (с указанием автора, кодировки UTF-8 BOM и описания назначения файла). Без этой шапки код считается невалидным.
  4. **Шаг 4: Документирование кода (Function Header)**: Все функции, методы виртуальных таблиц (VTbl) и важные внутренние алгоритмы внутри файла должны начинаться с комментария `Function Header` из Раздела 2.
- **Применение правил стиля**: Все правила кодирования, оформления заголовков, стандарты C89/MISRA, дисциплина памяти и правила выравнивания структур из разделов 1–3 текущего документа **строго применяются** ко всем генерируемым на основе шаблонов файлам.
